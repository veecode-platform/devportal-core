# DevPortal 3.1.0 release notes

DevPortal 3.1.0 moves the image from Backstage 1.52 to Backstage 1.54.9 and stays on the old frontend system. This page lists what changes for an operator upgrading from 3.0.x, what to check and what to edit before the upgrade.

## Backstage 1.54.9 on the old frontend system

3.1.0 runs Backstage 1.54.9, up from 1.52 in 3.0.x. It is built from Red Hat Developer Hub (RHDH) commit `3ac14d77` (Backstage 1.54.6), the last RHDH `main` commit before RHDH moved its app to the new frontend system. This release raises Backstage to 1.54.9. The move to the new frontend system is planned for v4.

The base images move from UBI 9.8 to UBI 10.2 and Node.js from 24.19.0 to 24.21.0. The dynamic plugin installer moves from 0.4.1 to 0.5.0. If a derived image or an init script assumes UBI 9 packages or paths, check it against UBI 10.

The image is `docker.io/veecode/devportal:3.1.0`, with digest `sha256:fe33373b7e5dc536f04d1878519bb53862a769b46869f78f829b198a30e5246b`. The `3.1.0-rc.3` tag points at the same digest. The release is the candidate that passed qualification, promoted by digest without a rebuild.

## Plugins that are no longer in the image

The 3.1.0 image has no `dynamic-plugins/` directory. RHDH removed its local plugin wrappers upstream, and this line carries the removal. The 3.0.3 image has 41 directories under `dynamic-plugins/dist/`.

An entry keyed by a former `./dynamic-plugins/dist/...` path is not an error. In a run of the 3.1.0-rc.1 installer with two such entries, it logged `Skipping 2 local plugins (directories not found)`, named each path, reported `All plugins installed successfully` and exited 0. The plugin is silently missing, and the `pluginConfig` of the skipped entry, if it has one, is still merged into the portal configuration. The effect of that leftover configuration in the UI was not checked. The 3.0.3 installer installs the same entries and logs `Installing NPM plugin ./dynamic-plugins/dist/...` for each.

Before you upgrade, search `global.dynamic.plugins` and any `dynamic-plugins.yaml` you mount for `./dynamic-plugins/dist/`. Search the Marketplace selections too, as described below. The [3.0.0 release notes](3.0.0.md#product-face-overrides) describe overrides keyed by a former path.

Replace each entry with the plugin's OCI reference, or remove it. [Installing Plugins](../dynamic-plugins/installing-plugins.md#loading-a-plugin-from-an-oci-image) describes the `oci://` form. Of the 146 packages in the 3.0.x catalog index (`bs_1.52.0`), 135 use OCI references and eleven use a `./dynamic-plugins/dist/...` path. Those eleven cover eight plugins: acr, adoption-insights, bulk-import, keycloak, pingidentity, quickstart, scaffolder-relation-processor and topology. The 3.1 catalog index lists all eight as OCI images.

Marketplace selections are stored in the `marketplace_installations` table. The table is in the Marketplace plugin's database, which is `backstage_plugin_extensions` when `backend.database.prefix` keeps its default, `backstage_plugin_`. Run the SQL below in that database. With `pluginDivisionMode: schema`, the table is in a schema of the portal's database instead. Find that schema with `SELECT table_schema FROM information_schema.tables WHERE table_name = 'marketplace_installations';` and write the table as `"<schema>".marketplace_installations` in the statements below. `package_name` holds the plugin reference, `disabled` holds whether the selection is turned off, and `config_yaml` holds the saved YAML, which can be empty. A selection of a former local plugin keeps its `./dynamic-plugins/dist/...` path in `package_name`, and the installer skips it the same way. In a run on 3.1.0-rc.1 with eleven rows seeded in the 3.0.x format, the plugin installer logged `Skipping 11 local plugins (directories not found)`, reported `All plugins installed successfully` and exited 0.

Reinstalling one of these plugins from the Marketplace adds a row for the OCI reference. The Marketplace does not merge that row with the old one, so both stay. If the two rows carry different `pluginConfig`, the install init container exits 1 with `defined differently for 2 dynamic plugins`. That failure was measured on 3.1.0-rc.1 with seeded rows, not through the portal UI.

Nothing in 3.1.0 converts these rows. Before you upgrade, list them and save each `disabled` and `config_yaml`:

```sql
SELECT package_name, disabled, config_yaml
FROM marketplace_installations
WHERE package_name LIKE './dynamic-plugins/dist/%';
```

After the upgrade, wait until the Marketplace lists the 3.1 version of each of these plugins (see the Known issues section below; it can take up to 30 minutes). Then, for each row that came back:

1. Reinstall the plugin from the Marketplace, and set its YAML to the saved `config_yaml`. If the saved row had `disabled` set to true, disable the new selection too.
2. Delete the old row once the new one is in place: for an enabled selection, after the plugin loads from the new row; for a disabled one, after you check that the new selection is disabled. The Marketplace has no route that removes the old row.

```sql
DELETE FROM marketplace_installations
WHERE package_name = './dynamic-plugins/dist/<plugin>';
```

Do not run these steps on 3.0.x. There the Marketplace still writes the `./dynamic-plugins/dist/...` path.

## Factory plugins come from the catalog index

The image no longer bakes in the list of plugins it enables. It carries `/opt/app-root/src/factory-plugins.yaml`, which names 18 plugins and marks four of them protected. The step that applies Marketplace selections before the plugins install reads that list to tell which Marketplace rows refer to one of these plugins. The 18 plugins come from the catalog index, enabled and with their configuration. The file `dynamic-plugins.veecode.yaml` that 3.0.x baked into the image is gone.

The four protected entries are `red-hat-developer-hub-backstage-plugin-catalog-backend-module-extensions`, `devportal-marketplace-backend`, `devportal-pending-changes-dynamic` and `devportal-marketplace-frontend-dynamic`.

For an operator, this means:

- A fix to one of these plugins ships as a new catalog index. The image does not change.
- Overrides in `global.dynamic.plugins` keep working. In a test on 3.1.0-rc.2 with a locally built copy of the catalog index, a `disabled: true` override with the full OCI reference removed its plugin from the install, and an override with a full `pluginConfig` applied the changed key. The `:{{inherit}}` form that the chart guide recommends was not part of that test. An override that names a plugin by a digest from chart 1.0.x keeps the build that digest names, not the one the index ships. Before you upgrade, replace `@sha256:<digest>` with `:{{inherit}}` and keep the `!<path>` suffix in each such override of a default plugin (see the chart's [override guide](https://github.com/veecode-platform/devportal-chart/blob/main/docs/product-face-overrides.md)).
- A `pluginConfig` saved in the Marketplace for one of these plugins is ignored, and the install log says so. Change its configuration in `global.dynamic.plugins` instead.
- A disabled Marketplace row for one of the four protected plugins is ignored, and the install log says so. The other factory plugins can be disabled from the Marketplace. In a test on 3.1.0-rc.3 with a real Postgres database, disabling the Tech Radar frontend removed it from the loaded plugins.

The Marketplace backend is 0.3.1 and its frontend is 0.3.2, both enabled by default. Invalid YAML is refused when you install a plugin or save its configuration, and the install page shows the line and column of the first error. The YAML you type on a plugin's install or edit page is saved as typed, except that an entry without `pluginConfig` still gets the package's first example. In 3.0.x, the configuration already saved or the package's first example was stored instead.

## Security fixes

3.1.0 locks `@backstage/plugin-scaffolder-backend` 4.1.0, which fixes GHSA-g2v8-7jhw-pp8p (CVE-2026-106501, critical, sensitive information exposure in the Scaffolder). 3.0.3 ships 4.0.1, which is in the affected range.

multer moves from 2.3.0 to 2.4.0, which fixes GHSA-3pph-fpjx-jg34 (medium, denial of service through orphaned disk writes on aborted uploads).

proxy-addr stays at 2.0.8, the fix for GHSA-jqcg-44mw-7w3h (critical, IP spoofing through an IPv4-mapped IPv6 trust subnet). The 3.0.3 host already resolved 2.0.8. RHDH's lock resolves 2.0.7, so 3.1.0 pins 2.0.8 with a `package.json` resolution.

The 3.1.0 image scan, run in block mode, reports no critical vulnerabilities. The 18 plugin artifacts enabled by default report none either.

## RBAC moves as a pair

`@backstage-community/plugin-rbac-backend` moves from 7.12.5 to 8.1.4, with `@backstage-community/plugin-rbac-node` 2.1.1 and `@backstage-community/plugin-rbac-common` 2.1.1. The RBAC frontend moves with it. The plugin enabled by default is RBAC frontend 2.3.1, loaded from the catalog index. The two must move together in both directions. rbac-backend 8 refuses the conditional-policy writes of frontend 1.52.4, and frontend 2.3.1 writes conditions that rbac-backend 7.12.5 refuses.

A REST run against rbac-backend 8.1.4 returned 201, 201, 200, 200, 204 and 204 for these calls: create a role, create a condition, read the conditions, update a condition, delete a condition and delete the role.

rbac-backend 8 adds no database migration. An upgrade from a database written by 7.12.5 was not tested.

## Versions kept at their 3.0.x levels

`@red-hat-developer-hub/backstage-plugin-translations-backend` stays at 0.3.1.

`@scalprum/core` 0.9.3 and `@scalprum/react-core` 0.11.2 stay pinned with resolutions, although the app declares 0.10.3 and 0.13.3. Removing the pins changes the plugin host runtime.

## Plugin catalog index

The 3.1 plugin catalog index is built for Backstage 1.54.9. It is published as `quay.io/veecode/plugin-catalog-index:bs_1.54.9`, with digest `sha256:26bd062a8fad8c204b1a175e775a4549d599a2a57acd849f083d6591ed2a917d`. Chart 1.1.0 pins this digest. The overlays change that builds it is merged, in the [devportal-plugin-export-overlays](https://github.com/veecode-platform/devportal-plugin-export-overlays) repository. The index also builds homepage, extensions, tech-radar, mcp-chat and mcp-integrations for 1.54.9.

The index moves these plugins to a new major version, from the 3.0.x index: argocd 2.8.0 to 3.1.3, rbac frontend 1.52.4 to 2.3.1, tekton 3.37.0 to 4.0.5, jfrog-artifactory 1.30.0 to 2.0.3, multi-source-security-viewer 0.15.2 to 1.0.3, analytics-provider-segment 1.27.0 to 2.0.0, global-header 1.21.6 to 3.1.0, tech-insights-backend 2.5.0 to 3.1.0, topology 2.12.3 to 3.0.7, bulk-import 7.3.5 to 9.1.1, quickstart 1.9.6 to 2.2.0 and adoption-insights 0.8.2 to 1.0.4. The four GitHub plugins (github-actions, github-deployments, github-discussions and github-pull-requests-board) move from 0.22.0, 0.18.0, 0.10.0 and 0.16.0 to 1.4.0.

The RBAC frontend and global-header are factory plugins too. They load from the index at RBAC frontend 2.3.1 and global-header 3.1.0.

Most of these majors make the new frontend system plugin the default export of the package and move the old exports to a `/legacy` subpath: argocd 3.0.0, rbac 2.0.0, tekton 4.0.0, jfrog-artifactory 2.0.0, multi-source-security-viewer 1.0.0, analytics-provider-segment 2.0.0, topology 3.0.0, bulk-import 8.0.0, quickstart 2.0.0 and adoption-insights 1.0.0. The changelogs describe this as a change of import paths for an app that compiles the packages in. The portal runs the old frontend system, so each of these ten workspaces ships a `scalprum-config.json` that sets `PluginRoot`, the default module, to the legacy entry. Without it, a missing export shows only as a console warning. The default configuration of tekton also names `module: Alpha` for its translation resource. If you override `pluginConfig` for one of these plugins, compare it with the default of the new version.

In the published images, every `PluginRoot` module has `createPlugin`, and all 35 metadata `importName` and `ref` values resolve. This is a module check. No browser run of these bundles is claimed.

Four moves have notes of their own.

The azure-devops backend moves from 0.27.0 to 0.32.0. When `azureDevOps` is set, its config schema requires `azureDevOps.pullRequestDashboard.organizations`, a list of entries with `organization` and `host`. Add it before the upgrade:

```yaml
azureDevOps:
  pullRequestDashboard:
    organizations:
      - organization: <your organization>
        host: dev.azure.com
```

The four GitHub plugins move from Material UI to Backstage UI (upstream 1.0.0). The host app ships `@backstage/ui` 0.17.1. The GitHub Discussions search module is rebuilt in this index and stays disabled by default. Its install from the Marketplace was not tested on 3.1.0.

bulk-import-backend moves to 9.1.1 in 3.1.0. From 9.0.0, it requires short-lived GitHub App installation tokens for the Orchestrator import mode, and fails closed when only a classic personal access token is available.

tech-insights-backend 3.1.0 has no documented breaking change. The upstream 3.0.1 notes say "No breaking changes" and replace a 3.0.0 that crashed on startup.

global-header moves to 3.1.0, the last version with a legacy entry. Upstream 3.2.0 removes the `/legacy` export and the legacy frontend plugin implementation. app-auth and app-integrations stay at 0.0.2, the version in the 3.0.x index.

## Chart

The chart that ships 3.1.0 is devportal-chart 1.1.0, released on 15 October 2026 and served by `https://veecode-platform.github.io/next-charts`. Chart 1.1.0 installs image 3.1.0 and pins the `bs_1.54.9` catalog index by digest. The previous release, 1.0.4, installs image 3.0.3 and pins the `bs_1.52.0` index. Each chart release re-pins the catalog index before the version is tagged. See the chart's [catalog index configuration](https://github.com/veecode-platform/devportal-chart/blob/main/docs/catalog-index-configuration.md).

Before you upgrade from chart 1.0.4, check these points:

- If your values still list `/opt/app-root/src/dynamic-plugins.veecode.yaml` in `global.dynamic.includes`, as the 1.0.4 default did, remove that entry. The 3.1 image has no such file, and the installer skips the missing include with a warning.
- Do not move to chart 1.1.0 with `helm upgrade --reuse-values`. It keeps the previous chart's defaults, including the 3.0.3 image and the `bs_1.52.0` catalog index. Pass explicit values instead, or use `--reset-then-reuse-values` with Helm 3.14 or later.
- If your values set `global.veecode.guestAuth.enabled`, keep that setting in the upgrade values. In the qualification run, an upgrade with values that omit it turned guest sign-in off.
- If an override of a default plugin names it by a digest, change it to the `:{{inherit}}` form, as described above.
- If your values set `global.catalogIndex.image`, check `repository` and `tag` together. From chart 1.1.0 the schema rejects a 64-character digest `tag` with a `repository` that does not end in `@sha256`, as well as a tag name with a `repository` that does. Remove the override to take the 1.1.0 default, or set both to a `bs_1.54.9` index your registry holds. The chart's [catalog index configuration](https://github.com/veecode-platform/devportal-chart/blob/main/docs/catalog-index-configuration.md) describes both forms and the mirror case.

## Known issues

The Red Hat Home page plugin is disabled by default in the 3.1 index, as it was in 3.0.x. The 3.0.0 known issue about it is not re-tested on 3.1.0.

The `veecode-theme` plugin is not in the 3.1 index. It was disabled by default in 3.0.x.

After an upgrade, the Marketplace can keep listing the packages of the previous catalog index for up to 30 minutes. The catalog reads the index through a scheduled task that runs every 30 minutes. In one run, the previous index's packages were still listed about 24 minutes after the upgrade. The task code shows that a restart or an upgrade does not run it sooner. During that window, a package installed from the Marketplace keeps the previous artifact until you reinstall it, and a former `./dynamic-plugins/dist/...` entry is skipped. Those two effects come from the code and were not observed in a run. Wait until the Marketplace shows the 3.1 versions before you install plugins. RHDH has the same lag, inferred from the same module code. It was not observed on RHDH.

## Qualification

The release qualification ran against the 3.1.0 image, with the chart 1.1.0 tree and the `bs_1.54.9` index, and finished with 0 failed checks. It covered an install on chart 1.0.4, a Marketplace install, the upgrade to this release, a Marketplace row for a package that does not exist, four restarts, a rollback to 1.0.4, and an upgrade with `guestAuth` omitted. The row for the missing package was skipped with a warning and listed under failed installs, and the other plugins still loaded.
