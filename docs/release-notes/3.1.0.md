# DevPortal 3.1.0 release notes

DevPortal 3.1.0 moves the image from Backstage 1.52 to Backstage 1.54.9 and stays on the old frontend system. This page lists what changes for an operator upgrading from 3.0.x, what to check and what to edit before the upgrade.

## Backstage 1.54.9 on the old frontend system

3.1.0 runs Backstage 1.54.9, up from 1.52 in 3.0.x. It is built from RHDH commit `3ac14d77`, the last RHDH `main` commit before RHDH moved its app to the new frontend system. The move to the new frontend system is planned for v4.

The base images move from UBI 9.8 to UBI 10.2 and Node.js from 24.19.0 to 24.21.0. The dynamic plugin installer moves from 0.4.1 to 0.5.0. If a derived image or an init script assumes UBI 9 packages or paths, check it against UBI 10.

The candidate image is `docker.io/veecode/devportal:3.1.0-rc.2`. The `3.1.0` tag is promoted from the approved candidate by digest, without a rebuild.

## Plugins that are no longer in the image

The 3.1.0 image has no `dynamic-plugins/` directory. RHDH removed its local plugin wrappers upstream, and this line carries the removal. The 3.0.3 image has 41 directories under `dynamic-plugins/dist/`.

An entry keyed by a former `./dynamic-plugins/dist/...` path is not an error. In a run of the 3.1.0-rc.1 installer with two such entries, it logged `Skipping 2 local plugins (directories not found)`, named each path, reported `All plugins installed successfully` and exited 0. The plugin is silently missing. The 3.0.3 installer installs the same entries and logs `Installing NPM plugin ./dynamic-plugins/dist/...` for each.

Before you upgrade, search `global.dynamic.plugins` and any `dynamic-plugins.yaml` you mount for `./dynamic-plugins/dist/`. Search the Marketplace selections too, as described below.

Replace each entry with the plugin's OCI reference, or remove it. [Installing Plugins](../dynamic-plugins/installing-plugins.md#loading-a-plugin-from-an-oci-image) describes the `oci://` form. Of the 146 packages in the 3.0.x catalog index (`bs_1.52.0`), 135 use OCI references and eleven use a `./dynamic-plugins/dist/...` path. Those eleven cover eight plugins: acr, adoption-insights, bulk-import, keycloak, pingidentity, quickstart, scaffolder-relation-processor and topology. The 3.1 catalog index lists all eight as OCI images.

Marketplace selections are stored in the `marketplace_installations` table. `package_name` holds the plugin reference and `config_yaml` holds the saved YAML. A selection of a former local plugin keeps its `./dynamic-plugins/dist/...` path in `package_name`, and the installer skips it the same way. In a run on 3.1.0-rc.1 with eleven rows seeded in the 3.0.x format, the install chain logged `Skipping 11 local plugins (directories not found)`, reported `All plugins installed successfully` and exited 0.

Reinstalling one of these plugins from the Marketplace adds a row for the OCI reference. The Marketplace does not merge that row with the old one, so both stay. If the two rows carry different `pluginConfig`, the install init container exits 1 with `defined differently for 2 dynamic plugins`. That failure was measured on 3.1.0-rc.1 with seeded rows, not through the portal UI.

Nothing in 3.1.0 converts these rows. Before you upgrade, list them:

```sql
SELECT package_name, config_yaml
FROM marketplace_installations
WHERE package_name LIKE './dynamic-plugins/dist/%';
```

For each row that comes back:

1. Save its `config_yaml`.
2. Reinstall the plugin from the Marketplace, and set its YAML to the saved `pluginConfig`.
3. After the plugin loads from the new row, delete the old row. The Marketplace has no route that removes it.

```sql
DELETE FROM marketplace_installations
WHERE package_name = './dynamic-plugins/dist/<plugin>';
```

## Security fixes

3.1.0 locks `@backstage/plugin-scaffolder-backend` 4.1.0, which fixes GHSA-g2v8-7jhw-pp8p (critical, sensitive information exposure in the Scaffolder). 3.0.3 ships 4.0.1, which is in the affected range.

multer moves from 2.3.0 to 2.4.0, which fixes GHSA-3pph-fpjx-jg34 (medium, denial of service through orphaned disk writes on aborted uploads).

proxy-addr stays at 2.0.8, the fix for GHSA-jqcg-44mw-7w3h (critical, IP spoofing through an IPv4-mapped IPv6 trust subnet). The 3.0.3 host already resolved 2.0.8. RHDH's lock resolves 2.0.7, so 3.1.0 pins 2.0.8 with a `package.json` resolution.

## RBAC moves as a pair

`@backstage-community/plugin-rbac-backend` moves from 7.12.5 to 8.1.4, with `@backstage-community/plugin-rbac-node` 2.1.1 and `@backstage-community/plugin-rbac-common` 2.1.1. The RBAC frontend moves with it, and the product face pins RBAC frontend 2.3.1. The two must move together in both directions. rbac-backend 8 refuses the conditional-policy writes of frontend 1.52.4, and frontend 2.3.1 writes conditions that rbac-backend 7.12.5 refuses.

A REST run against rbac-backend 8.1.4 returned 201, 201, 200, 200, 204 and 204 for these calls: create a role, create a condition, read the conditions, update a condition, delete a condition and delete the role.

rbac-backend 8 adds no database migration. An upgrade from a database written by 7.12.5 was not tested.

## Versions kept at their 3.0.x levels

`@red-hat-developer-hub/backstage-plugin-translations-backend` stays at 0.3.1.

`@scalprum/core` 0.9.3 and `@scalprum/react-core` 0.11.2 stay pinned with resolutions, although the app declares 0.10.3 and 0.13.3. Removing the pins changes the plugin host runtime.

## Plugin catalog index

The 3.1 plugin catalog index is built for Backstage 1.54.9. It is published as `quay.io/veecode/plugin-catalog-index:bs_1.54.9`, with digest `sha256:f4ce21b7b10df9645c90e2925c4ced9e8203337bdd47854782f8979268d3ff94`. The overlays pull request that builds it, [devportal-plugin-export-overlays#287](https://github.com/veecode-platform/devportal-plugin-export-overlays/pull/287), is merged. The index also builds homepage, extensions, tech-radar, mcp-chat and mcp-integrations for 1.54.9.

The index moves these plugins to a new major version, from the 3.0.x index: argocd 2.8.0 to 3.1.3, rbac frontend 1.52.4 to 2.3.1, tekton 3.37.0 to 4.0.5, jfrog-artifactory 1.30.0 to 2.0.3, multi-source-security-viewer 0.15.2 to 1.0.3, analytics-provider-segment 1.27.0 to 2.0.0, global-header 1.21.6 to 3.1.0, tech-insights-backend 2.5.0 to 3.1.0, topology 2.12.3 to 3.0.7, bulk-import 7.3.5 to 9.1.1, quickstart 1.9.6 to 2.2.0 and adoption-insights 0.8.2 to 1.0.4. The four GitHub plugins (github-actions, github-deployments, github-discussions and github-pull-requests-board) move from 0.22.0, 0.18.0, 0.10.0 and 0.16.0 to 1.4.0.

The RBAC frontend and global-header are also product face plugins. The face pins them to `bs_1.54.9` builds: RBAC frontend 2.3.1 and global-header 3.1.0. The version that loads is the one pinned in the face baked into the image. The index version is the one the Marketplace shows.

Most of these majors make the new frontend system plugin the default export of the package and move the old exports to a `/legacy` subpath: argocd 3.0.0, rbac 2.0.0, tekton 4.0.0, jfrog-artifactory 2.0.0, multi-source-security-viewer 1.0.0, analytics-provider-segment 2.0.0, topology 3.0.0, bulk-import 8.0.0, quickstart 2.0.0 and adoption-insights 1.0.0. The changelogs describe this as a change of import paths for an app that compiles the packages in. The portal runs the old frontend system, so each of these ten workspaces ships a `scalprum-config.json` that sets `PluginRoot`, the default module, to the legacy entry. Without it, a missing export shows only as a console warning. The default configuration of tekton also names `module: Alpha` for its translation resource. If you override `pluginConfig` for one of these plugins, compare it with the default of the new version.

In the published images, every `PluginRoot` module has `createPlugin`, and all 35 metadata `importName` and `ref` values resolve. This is a module check. No browser run of these bundles is claimed.

Four moves have notes of their own.

The azure-devops backend moves from 0.27.0 to 0.32.0. When `azureDevOps` is set, its config schema requires `azureDevOps.pullRequestDashboard.organizations`, a list of entries with `organization` and `host`. Add it before the upgrade:

```yaml
azureDevOps:
  pullRequestDashboard:
    organizations:
      - organization: <your organization>
        host: dev.azure.com
```

The four GitHub plugins move from Material UI to Backstage UI (upstream 1.0.0). The host app ships `@backstage/ui` 0.17.1.

bulk-import-backend moves to 9.1.1 in 3.1.0. From 9.0.0, it requires short-lived GitHub App installation tokens for the Orchestrator import mode, and fails closed when only a classic personal access token is available.

tech-insights-backend 3.1.0 has no documented breaking change. The upstream 3.0.1 notes say "No breaking changes" and replace a 3.0.0 that crashed on startup.

global-header moves to 3.1.0, the last version with a legacy entry. Upstream 3.2.0 removes the `/legacy` export and the legacy frontend plugin implementation. app-auth and app-integrations stay at 0.0.2, the version in the 3.0.x index.

## Chart

The chart that ships 3.1.0 is devportal-chart 1.1.0, which is not released yet. The latest chart release is 1.0.4. It installs image 3.0.3 and pins the `bs_1.52.0` catalog index by digest. Each chart release re-pins the catalog index before the version is tagged, so chart 1.1.0 is expected to pin the `bs_1.54.9` index. See the chart's [catalog index configuration](https://github.com/veecode-platform/devportal-chart/blob/main/docs/catalog-index-configuration.md).

## Known issues

The product face pins 19 of its 20 entries to `bs_1.54.9` builds, including RBAC frontend 2.3.1 and global-header 3.1.0. The `veecode-theme` entry keeps its `bs_1.49.4` pin. The face pin gate checks each digest and artifact version against the published index. It does not run the plugins.

The 3.0.0 known issue about the Red Hat Home page entry is not re-tested on 3.1.0. The face still ships that entry disabled.

The release qualification of the 3.1.0 candidate (install, Marketplace install, upgrade from the previous chart, restarts and rollback) has not run yet.
